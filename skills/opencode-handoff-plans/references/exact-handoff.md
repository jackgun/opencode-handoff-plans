# 精确执行计划与交接

适用于设计已定、要求按参考实现复现的任务。契约式计划不必提供全部实现。下列路径、任务数量、围栏长度和测试数字均由实际项目确定，不沿用参考项目的值。

## 开头先固定执行条件

写清目标、设计链接、基线提交、指定分支和工作目录、允许修改的文件，以及已授权的提交、推送与发布范围。已有工作树应明确复用；运行环境位于其他目录时，区分“借用解释器”和“在那里修改或运行项目”。

环境表至少包含：

| 项目 | 必填信息 |
| --- | --- |
| 命令环境 | Shell、每组命令的工作目录、解释器或工具路径、必要环境变量 |
| 依赖复用 | 已有 venv、构建产物或服务的位置与检查方式 |
| 验证范围 | 定向测试、必要回归、清单校验或构建各自的完整命令 |
| 环境缺口 | 受影响测试/命令、失败原因与证据、排除参数、补跑负责人及前提 |
| 已知失败 | 基线提交、失败测试名称及原因；与本轮新增失败分开 |
| 实测记录 | 交接前逐项实测的日期与结果：服务/容器是否在运行、端口归谁、凭据能否登录、库或 schema 是否已初始化 |
| 相邻危险目标 | 同机或同网络中不得连接、停止、重建的服务、端口、库和目录，及其归属 |

环境表必须在交接前实测，不能沿用旧计划或旧笔记。实测与记录不符时，先修正环境或计划，再交接；例如原测试数据库容器已停、原端口已被另一部署栈占用、凭据对不上时，改用新建的专用测试服务和独立端口，并把原端口作为相邻危险目标写进红线。只写“使用哪个”不够：指定目标连不上时，执行者容易改连相邻的那个。

真实数据库或服务的测试若依赖环境变量，把变量写在测试命令的同一行：代理的各次工具调用通常不共享 Shell 状态，上一条 `export` 不会生效，测试就会整体 skip。计划声称某条规则由真库验收时，把“真库测试 skip 数为 0”写成交付门槛。

涉及字节级黄金文件或 hash 的仓库，在 Windows 上确认 `core.autocrlf` 为 `false`（或用 `.gitattributes` 固定换行）；多行文件内容用文件写入工具落地，不用 heredoc，避免引号和结束标记被 Shell 改写。

命令必须适配声明的 Shell，明确后续 `cd` 的起点。工作树使用外部解释器时，确认导入的源码仍来自目标工作树。不要为凑出通过结果自动装依赖、切回主目录、扩大忽略范围或修改无关测试。

排除的测试属于待验收项。将 `validate` 通过、构建通过及外部验收通过分别报告；不能用一个替代另一个。未知测试数量写“待实测”，不要根据历史报告推算。

## 按任务提供可复制操作

每个 Task 列出新增/修改文件、消费的前置产物和输出给后续任务的符号或契约。按用户或仓库要求固定顺序、提交粒度；要求逐任务执行时，独立任务也不能擅自合并或并行。

采用先红后绿的任务逐项写成：

1. 写测试：提供测试全文或精确替换块。
2. 确认失败：给完整命令、失败测试及预期错误原因。
3. 实现：按顺序列出每个文件操作。
4. 确认通过：给完整命令、行为断言及回归范围。
5. 提交：仅暂存该任务列出的文件，给提交信息；偏差修正单独记录。

执行者若使用按标题解析任务的脚本（例如生成任务简报或维护 ledger 的工具），任务标题采用脚本可识别的格式，例如 `### Task N: 标题`；自定义编号（如 `### T0.1：`）会让脚本找不到任务。无法改标题时，在交接中写明 ledger 由人工维护、每行格式及基线提交的取法。

只做验证的 Task 标明“不改文件”，不强加红绿步骤或空提交。首次新增模块的 ImportError 可以证明尚未实现，但业务反例仍需有效断言。

代码材料遵循以下格式：

- **新文件：** 路径 + 全文；不使用省略号、“其余同上”或未定义的辅助函数。
- **已有文件：** 路径 + 查找原文 + 替换全文。查找块包含足以唯一定位的上下文；同一文件的多次替换按应用顺序验证，后一步面对的是前一步修改后的内容。
- **逐字范围：** 明确围栏内部的中文标点、空行和缩进也须保留，围栏本身不进入文件。内容含 Markdown 围栏时使用更长的外层围栏；五个反引号只是可选方式。
- **匹配门槛：** 每次替换前必须恰好匹配一处。零处或多处均停止该步骤并报告，不模糊匹配、不全局替换、不猜第几处。文件已存在或替换后内容已存在也先核对，不能覆盖已有工作来假装从零执行。

## 交付前演练

作者在获准的隔离环境或临时副本中，从记录的基线按计划原文顺序重放：新文件全文落地、每处查找唯一匹配、逐步验证、最终 diff 与参考实现比对。临时副本的文本重放只能证明补丁可应用；未运行测试时不能称“实现已跑通”。用户限制工作区时不擅自另建工作树。

记录演练基线、环境、日期、命令、退出码和实际输出摘要。逐字比对时说明比较范围及换行规范；不把语义一致称作字节一致。预期结果与实测结果分栏，耗时只作证据，不作为稳定门槛。只有明确锁定基线且确有需要时才把测试数量设为停止条件，否则按失败身份、原因和新增回归判断差异。

发现重复锚点时，由作者扩充上下文并重放验证后再交付。无法演练则列出未验证步骤及接手条件，不把“已有参考代码”包装成“已经按计划跑通”。

## 偏差处理契约

在交接中明确下面两类，执行者按已授权范围处理：

| 情况 | 动作 |
| --- | --- |
| 范围内、未改变设计与验收口径的必要修正 | 记录证据；能测试表达的先补回归测试；单独提交，报告原因及影响 |
| 精确替换零匹配/多匹配、触及红线、改变设计、改验收集或门槛、超出允许文件 | 停止受影响步骤，记录并请求决策；严格串行时不继续依赖它的后续任务 |

偏差记录固定为：`Task/Step → 计划原文 → 实际情况及输出 → 影响范围 → 已做/建议修正 → 回归测试 → 提交或待决策状态`。无需修改时也记录环境阻塞，不把它编造成代码缺陷。

## 红线写法

红线写成可核对的禁止动作及其出口（遇到时按偏差处理），按项目选用：

| 红线 | 出口或例外 |
| --- | --- |
| 不安装、不升级依赖 | 缺包按偏差报告，写明缺哪个包、哪条命令受影响 |
| 不执行 `compose down`、不删 volume、不重建已有容器；不连接相邻危险目标 | 只使用环境表列出的专用服务 |
| 只读仓库不改文件 | 计划点名的新增文件单独提交；临时文件用完删除，`git status --porcelain` 为空 |
| 不发送真实消息、不调用真实模型 | 写明例外任务、使用哪个已配置档位、结果记为人工证据；不可用时记 `blocked`，不用假实现结果替代 |
| 黄金值不得修改 | 认为有误时报告，并附从原始资料截取的原文 |
| 大模型提示词不写样本的结论、原名或专有数值，只写分析方法 | 防止对唯一样本过拟合或泄漏；需要示例时使用虚构数据 |
| 不推送、不部署 | 由验收方或用户统一处理 |

场景：执行者为让唯一样本的端到端测试命中全部发现项，在提示词里写入“该企业存在某项问题”。测试通过，但换一份输入就失效，且样本原名进入了模型输入。有了“提示词只写分析方法”这条红线，执行者只能改进分析方法，或者报告偏差。

## 交接与回报

交接开头写明：验收不采信报告，验收方会在相同基线自行重跑。报告的作用是说明做了什么、在哪里可以核对，而不是替代验收。

可粘贴开场提示词应包含：项目目标、工作区与分支、计划路径与起始任务、必读文件顺序及具体章节、执行模式、运行环境、偏差规则、禁止或已授权的发布操作。它引用详细规则，不复制一套容易漂移的命令清单。

回报槽位：

```text
分支/HEAD/工作目录：实际值
提交与推送状态：已提交/未提交；已推送/未推送（按事实填写）
逐任务提交：Task、提交哈希、信息；验证任务填写无代码提交
验证：工作目录、完整命令、退出码、实际摘要、pass/fail/skip
红绿证据：每个任务失败时与通过时的输出摘要各 1～3 行
核对项：计划中标为“核对/实测”的事项，结论 + 证据（文件:行号或命令输出）
人工证据：截图、真实外部调用结果的位置；不可用时写 blocked 及原因
已知失败/新增失败/未运行或排除项：分别列明
偏差：Task/Step、原文、证据、处理、回归测试、提交或待决策
待验收项：负责人、环境前提、补跑命令、完成门槛
```

发布前复查公开材料：使用通用示例，不带真实客户数据、内部仓库地址、个人绝对路径或凭据；通用技能不固定某项目的业务开关、语言、忽略测试数量或验收方姓名。
