# 多线分波次的计划与交接

适用于编写拆成多个波次、每波多条开发线由不同执行者并行完成、由验收方（代理或人）逐线验收的计划与交接文档。单线任务只需 [exact-handoff.md](exact-handoff.md)。下文的波次数、线名、标签名和目录均为示例，按实际项目确定。

下列做法均来自真实交付中已遇到并处理过的问题。

## 契约波：先冻结，再分发

骨架、共享类型、数据表迁移、公式或协议求值器等被多条线共同依赖的内容，放在第 0 波，由验收方或指定的集成负责人串行完成。完成后打标签（例如 `contract-v1`），并行线的工作区和分支由验收方从该标签创建。执行者不建工作区、不切分支、不合并其他线。

场景：五条线同时开工，其中两条都“顺手”补了同一个共享类型的字段，合并时一条线的语义被静默覆盖。若共享类型在标签之前已冻结，且只有验收方能建分支，两条线都必须按偏差停下来报告，冲突在分发前就暴露。

契约波执行中产生的 Ruling（对计划的解释、补充或修正），在分发前必须先写回计划：

1. 把每条影响后续线的 Ruling 改进计划正文（任务卡、契约表或交接文档），形成一次单独的“计划同步”提交。
2. 标签重新指向同步后的提交；已建好的线工作区快进到该提交。
3. 然后才把开场提示词交给执行者。

场景：契约波实测发现宿主部署清单每个条目都要求某个必填字段，且映射类型的年份键只能是字符串。若只记在执行 ledger 里，负责部署文件的线会照计划原文写出缺字段的清单，负责计算输出的线会用整数年份键，二者都会在验收时才失败。

序列化语义在契约层写死，不留给各线自行决定：十进制数用带类型标记的编码，映射键只允许字符串，时区和舍入方式固定。契约若声称“编码再解码等于原值”，所有已知不满足的情况都要写进计划的契约章节，作为**消费方约束**，例如“表格类型会丢弃目录未声明的列”“元组往返后变为列表”。不能只作为暂缓的小问题留在 ledger 里。

场景：一条线按“往返相等”写了断言，用元组构造期望值；另一条线在表格里多放了一列说明。前者测试失败被误判为自身缺陷，后者的列在持久化后消失而无人察觉。计划里写明这两条消费方约束，两条线都会在编码前按约束设计输出。

两条并行线都会用到的类型，包括一条线定义的协议的参数和返回值类型，也放进契约波；不要写成“实现某线定义的协议”。场景：一条线按另一条线将要定义的协议实现，自己先定义了一份同名数据类，合并时出现两份定义。跨线共用的判定逻辑（校验器、规范化函数、格式化函数）同样放进契约波，或指定唯一负责线；否则两条线各实现一份，规范化规则也不一致。

下游线为了并行开发，按原始资料手写了输入夹具来代替上游的真实输出时，计划要安排一次“夹具 vs 真实输出”的差异比对：放在上游合入之后、下游集成之前，由验收方或集成任务负责。任何差异都要判定是哪一方错了，不能默认以夹具为准。场景：两条线各自的测试都通过，比对时下游按原文手写的正确值，暴露出上游解析出的值是错的。

交接文档逐一点名共享契约文件，作为执行者不得修改的清单；需要改动时按偏差处理停下来报告，由验收方统一修改并发布新标签（例如 `contract-v2`）。

在契约波里就用宿主真实的校验工具（插件清单校验、schema 校验、构建检查等）跑一次，不等到最后一波的集成任务。校验需要在只读仓库放临时文件时，用完删除，并以该仓库 `git status --porcelain` 为空作为证据。宿主静态扫描若按字面匹配（禁用 import、禁用 API、裸表名等），受扫描文件的**注释和文档字符串**也要避开禁用词；在计划中提醒，而不是等扫描失败后改注释。

场景：计划只在最后一波安排宿主校验。契约波按计划写的清单字段通过了本地测试，但宿主校验要求一个计划没列出的必填字段；后续所有线都已按旧清单工作，修正需要跨线返工。

## 交接文档骨架

多线交接用一份交接文档，内容依次为：

1. **分工声明**：谁执行、谁验收、谁合并；写明“验收不采信报告，验收方会自己重跑一遍”。
2. **波次对照表**：`波次 | 线 | 工作区 | 分支 | 前置条件`；前置条件写具体标签或“上一波全部合入”。
3. **单一开场提示词模板**，加每线任务列表表格。不为每条线各写一份提示词，避免内容漂移。
4. **必读顺序**，含“线 → 必读设计章节”映射表；每条线只读与之相关的章节，不要求通读全部设计。
5. **只读参照实现清单**：可参考的现有仓库、SDK、协议文档，明确只读。
6. **红线**：通用条目见 [exact-handoff.md 的红线写法](exact-handoff.md#红线写法)，另加本项目共享契约文件清单。
7. **偏差处理**：沿用 [exact-handoff.md 的偏差处理契约](exact-handoff.md#偏差处理契约)，列出本项目常见的停止情况（共享契约要改、宿主实际行为与计划不符、原始资料与黄金值不一致、需改独占目录外的文件）。
8. **交付报告格式**：见 [exact-handoff.md 的回报槽位](exact-handoff.md#交接与回报)。
9. **验收方检查清单**：执行者也可以提前自查。

开场提示词模板：

```text
在 <工作区>、分支 <分支> 执行 <计划路径> 中「<线>」这一线的任务：<任务列表>。
设计依据是 <设计路径>。
开工前先按交接文档 <交接路径> 的「必读顺序」阅读，遵守其中的「红线」。
每个任务先写失败的测试并运行确认失败，再实现并运行确认通过，然后独立提交一次。
只修改计划中分配给本线的独占目录，以及本线新增的测试文件。
共享契约（<契约文件清单>）不得修改；如需改动，按「偏差处理」停下来报告。
全部完成后，按「交付报告」的格式回报。
```

验收方检查清单骨架（按项目裁剪）：

```text
1. 守卫测试：每一条都注入过违规样本，确认失败后再恢复；提交说明或报告里有记录。
2. 真库测试 skip 数为 0；环境变量与测试命令写在同一行。
3. 黄金值断言与计划逐项一致，没有被放宽（例如用近似比较替代精确比较）；断言右侧是字面值，而不是用同一公式重算。
4. 生产接线：从入口出发逐行核对账本，每个注册点在代码中真实存在。
5. 跨模块规则（例如“模型输入不含真实名称”）的证据来自完整链路组合测试，而不是只测单个函数。
6. 只读仓库 `git status --porcelain` 为空（计划授权的新增文件除外）。
7. 宿主校验工具通过；静态扫描的字面量约束满足。
8. 报告里的“基线既有失败”或“与本线无关的失败”，先在基线提交上用计划规定的同一命令复现；复现不出的按本线失败处理。
```

## 守卫测试与评审重点

守卫测试（禁止某些 import、禁止读取环境变量、禁止裸表名等）逐条注入违规样本，确认测试会失败，再移除样本。未做注入验证的守卫测试不计入验收证据。

场景：守卫测试用正则扫描 `src/`，但路径拼写错误导致扫描零个文件，测试永远通过。只有注入一个违规样本，才会发现它从未生效。

用户可编辑的表达式、规则或模板求值器，除语法白名单外还要限制运算的**操作数类型**。Review Focus 列入“白名单内的合法构造组合起来造成资源耗尽”这一类：例如字符串乘法与 `len()` 连乘可以生成极大字符串耗尽内存，而每个节点都在白名单内。修复前先写能复现的测试，确认失败，再转绿。
