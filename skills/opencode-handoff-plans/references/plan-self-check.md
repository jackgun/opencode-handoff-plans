# 从规则推导高风险场景与计划自查

计划可能含有错误事实，执行者也可能遗漏已经写明的要求；不能只凭代码整洁、测试数量或守文件边界判断根因。本文件用于写任务卡和交付前自查：从每条写库、改状态或做计算的规则，选择适用场景，写明真实输入、调用与最终断言。关键字段生命周期、最小贯穿样例和返工证据槽位见 [delivery-evidence.md](delivery-evidence.md)。

下列做法均来自真实验收中已复现的缺陷。

## 从每条规则推导的场景

| 规则形态 | 计划必须写明 | 必配测试 |
| --- | --- | --- |
| 批量迁移新增带兼容默认值的参数 | 参数从可信配置到首次数据投影、全部实际入口、序列化/回调和最终出口的传播；先做哪条贯穿样例 | 非默认配置经真实下载/定时等入口触发，测试不手动补缺失参数；同时检查正文、明细或实际消费者，默认旧回归保留 |
| 显示文字引导用户下一步输入 | 区分显示标签、内部动作和宿主规范化后的输入；明确排除词表扩展与消费本次新指令的边界 | 原样使用已显示命令，经真实入口完成下一步；点击与自由文本分别检查，拒绝样例保留同前置的合法输入对照 |
| 同一实例切配置并复用缓存/已加载数据 | 真实缓存键、组件依赖、请求数据刷新与历史生成内容的识别边界 | A→B→A，经过实际缓存/消费者并保留用户草稿；直接读取 getter、mock 掉投影或重启后通过均不能证明切换 |
| 同页面读取与保存/上传/批量操作会重叠 | 分清读取快照、业务提交与响应送达，列全部数据写入入口及成功后的收敛时点；确定哪些筛选/草稿保持、哪些表单成功后清理 | 新上下文先读到旧状态再发生业务提交；操作成功后旧读取才送达。两种顺序均检查当前上下文、筛选和成功后的业务内容，不只检查 locale/请求序号；允许修复追加合法刷新，见 rework-control.md 的时序样例 |
| 测试依赖某个前置状态（已编辑、已发布、已同步） | 前置状态经哪条生产调用链构造；禁止直接改库、给字段赋值或伪造标记 | 用该调用链构造前置状态后再断言；验收时检查测试里有没有直接改状态的 SQL 或赋值 |
| 记录由启动、定时、重试、重新同步等会反复触发的入口产生 | 去重键（哪些字段组合唯一）及冲突时的行为 | 同一触发重复 N 次，只产生 1 条记录 |
| 先检查、后写入（版本未过期、只允许一次、状态必须是 X） | 当作竞争条件：加锁方式或 CAS 条件，以及 rowcount 为 0 时怎么处理 | 顺序版一条；并发版用两条独立连接加线程屏障，断言只有一方成功、另一方的内容没有静默覆盖 |
| 接口按 id 或编号引用另一条记录（锁定版本、覆盖参数、外键参数） | 合法范围：状态白名单、归属一致性（同一条目、同一租户）、不合法时的返回 | 每一项范围各一个反例：引用草稿、引用别的条目、引用别的租户 |
| 操作带进程内缓存或“已完成”标记 | 谁提交事务；标记只在持久化成功之后写入 | 提交失败或调用方回滚后，标记未写入，下次调用会重做 |
| 被测数据由后续开发线交付（种子、目录、模板） | 本任务使用的测试夹具 | 断言非平凡的值，例如第一次导入数量大于 0；再问“如果实现什么都不做，这个测试会失败吗” |
| 接口向 UI 或 API 返回失败 | 从下游消费者反推它需要的诊断信息（字段、位置、原因），写进返回契约 | 断言错误明细到达消费者，而不只断言错误码 |
| 接口约定了异常类型或错误码（例如“解析不了时抛出某领域异常”） | 每种异常或错误码的触发条件 | 每种一个点名测试，用真实的非法输入触发（空、错误格式、截断），断言异常类型，并断言底层库的异常不会泄漏出来 |
| 结构性解析规则（跨页续表、折行合并、多行表头） | 写成对所有表格适用，不只写在某一个章节；要求执行者列出源文档中实际出现这种情况的全部位置 | 每个位置一个测试，或用下文的全量勾稽断言兜底 |
| 计算组件消费可能缺失的数据（单元格为“-”、上游未产出、整行缺失） | 空值规则表：每个输入为 None 或整行缺失时，输出及下游处理；覆盖总体、受影响分组、明细和说明；区分零样本与全部样本无效，保留有效／排除数 | 每个消费方分别断言值、状态及样本；不能总体待核实而分组给确定完成率，也不能全部缺期限时排除数为 0 |
| 按名称或键查封闭的表（费率表、映射表、枚举） | 查不到时的行为：跳过、标注人工确认或报错 | 用一个表外值，断言按所写行为处理，而不是抛出未处理的 KeyError |
| 输入是截断或抽样数据（前 N 名、分页、摘要） | “不在列表中”代表什么：未知、低于阈值，还是确实为 0 | 用一个不在列表中的项，断言按所写语义处理，不当作 0 |
| 任务产出宿主会消费的配置（compose、清单、路由、UI 注册） | 本任务内用宿主真实工具跑一遍校验和生成，并附上输出；不只在契约波或最后的集成任务里跑 | 宿主工具的校验和生成输出；被宿主禁止的写法（例如未固定版本的镜像）在本任务就暴露 |
| 过滤、脱敏、校验类规则（删除金额、校验文号、屏蔽名称） | 按字段语义确定保护范围，区分自由文本与结构标识；对抗样本含正文嵌入、全半角／空白等变体；同类兄弟规则及豁免各有反例 | 每类敏感特征单独命中，不靠同格另一特征；安全描述及含相似子串的合法 ID 保留，最终键集合与关联完整 |
| 合规或安全上必须存在的内容或配置（免责声明、水印、密钥、白名单） | 缺失或为空时失败并阻断交付（fail-closed），不静默跳过 | 缺失和空值各一个测试，断言交付被阻断 |
| 序列化、渲染、导出类任务 | 字段去向表：每个承诺字段在各输出的位置，或有意不输出的理由；共同写格入口涵盖文本类型、限长及隐私策略，说明页等出口不绕过 | 用真实来源的非空值逐字段读回最终产物；不只查表头；指标的值、状态、有效／排除样本都有对应出口 |
| 服务端解析或渲染不可信内容（模型输出、用户上传、外部文档） | 允许访问的资源范围：外部 URL、`file://`、本地路径默认禁止；渲染库默认会抓取引用资源时，写明关闭方式 | 引用外部 URL 和 `file://` 的样本，断言没有发起访问、没有读入本地文件 |
| “输出必须能在输入中找到来源”的校验（数字溯源、引用校验） | 来源集合：每种输入类型（标量、字符串、按键映射、结构化对象、嵌套记录）怎么展开成可比较的值；最好先规范化成与序列化相同的形态再收集 | 每种输入类型一个“引用它就应该通过”的测试。与上面的对抗样本集配对：那一行防漏过，这一行防误报 |
| 隔离、过滤、脱敏类要求 | 列出系统的全部出口：中间读取、最终返回值、持久化、日志、导出给下游的内容 | 每个出口一个断言，并带对照组：先在不过滤的级别确认敏感项确实存在，再断言它在过滤级别的每个出口都不出现 |
| 组件支持断点续跑、重试或幂等重放 | 每种中间状态（完成、失败、跳过、降级）是复用、重跑还是覆盖；持久化用 upsert 还是 insert；尝试次数怎么记 | 先失败、再成功，第二次写入不报错，且结果与状态记在正确的节点名下 |
| 持久化或序列化任务 | 一份覆盖契约里所有值类型的往返夹具：每种类型一个真实形态的样本，含嵌套结构、负数、None、整数键 | 读回的值用 `==` 与原值比较，并断言类型一致；只存一个标量不算覆盖 |
| 任务调用大模型（多轮、重试、结构化输入） | 每一轮的消息序列（角色、内容来源；重试时先把模型上一轮回答作为 assistant 消息带回）；输入的编码函数（与持久化用同一个）、字符集设置和字段顺序 | 断言重试时的消息序列；断言渲染后的输入里没有语言运行时的 repr 痕迹和转义序列 |
| 测试用替身代替宿主接口（认证依赖、存储、附件、消息通道） | 替身必须复现真实接口的签名和失败方式：认证依赖要求凭据、没有凭据时抛 401；存储 key 是否为内容摘要、相同内容是否去重。计划写明真实接口所在的文件和行，供执行者对照。认证或取角色失败一律拒绝，不得退回默认身份、默认租户或默认角色 | 用与真实签名一致的替身跑“未认证返回 401”“角色为空时无权限”；验收时把替身换成按真实签名写的版本再跑一遍 |
| 变换类功能（还原代号、脱敏、映射、格式化） | 测试输入中必须有会被变换的内容 | 断言变换前后的输出不同、且等于预期；“原样返回”的空实现会让测试失败 |
| 一个阶段写入、另一个阶段读出的持久化字段（JSON 列、可空列、数组列） | 读回时的类型（例如 JSON 列读出就是列表或字典，不能再按字符串解析） | 集成测试中每个这类字段至少用一个非空值走一遍真实数据库；样本恰好取到空的默认值时，另补一个非空样本 |
| 防重复的标记（“已通知”“已处理”）可能被多个流程写入 | 每个标记只守护一种事件，写明归属；别的流程不得占用 | 跨流程序列测试：失败（发失败通知）→ 重跑 → 成功，断言成功通知照常发出 |
| “任何异常都把状态标为失败”这类失败路径 | 先回滚当前事务，再写失败状态；写失败状态本身出错时怎么记录 | 注入数据库层的错误（例如执行一条非法 SQL），不只是抛一个普通异常；断言状态为失败且带原因，而不是停在进行中 |
| 计划冻结了版本（执行计划、锁定版本、试跑用草稿） | 冻结之后的每一次读取都按冻结的版本 id，不读“当前发布版” | 在规划和执行之间发布一个新版本，断言执行的仍是冻结版本；试跑时断言草稿内容真的生效 |
| 函数签名中的每个参数（尤其是布尔开关和可选参数） | 每个参数对输出的影响 | 每个参数一个测试：只改这个参数，输出随之改变；被忽略的参数会让测试失败 |
| 删除宿主存储中的对象（保留期清理、撤回样本） | key 是否可能被多条记录共享；删除前怎么查其他引用；删除失败时不清空引用 | 两条记录共用同一对象时，删掉一条，另一条仍能读到；存储删除失败时引用保留，下次重试 |
| 面向用户的文字中带出内部值（枚举、代码、状态名） | 每个内部值的显示文字；模板只能引用已映射成显示文字的字段 | 断言输出中不含内部代码（例如英文枚举值） |
| 参考数据由执行者录入（法规文号、费率、编码表） | 每条附来源链接，交付报告中给逐条核对表（编号、来源上的值、是否一致）；来源核不到的标注“待人工确认”，不凭记忆填写。测试期望值来自来源，不能来自执行者录入的同一份数据 | 验收方用独立来源抽查；抽查发现一条错误，就要求执行者全量重核 |
| 并行开发的接口线与界面线之间的响应 | 端点表写到字段名和类型，不只写“调用次数”这类描述；界面线只能使用表中的字段 | 接口测试断言表中每个字段都在响应里；验收时核对界面引用的每个字段都在表中 |
| 需要构建或打包的产物（前端页面、类型检查、镜像） | 验收命令用宿主实际构建时会跑的构建或类型检查，并写明宿主结构校验覆盖不到的内容（例如 import 路径能否解析、类型错误） | 构建或类型检查的输出；只跑结构校验不算通过 |
| 靠导入副作用填充的注册表（算子、插件、处理器、路由） | 由谁在什么时候加载：注册表首次查询时自己加载，或点名一个启动任务负责；不能依赖“某个接口碰巧先调用了加载函数” | 在新进程里不调用加载函数，直接查询注册表，断言内置项都在；测试和夹具里不得手动调用加载函数，否则会掩盖生产中没人加载的问题 |
| 引擎遇到缺失的作用域输入（年份列表、行表、分组键） | 缺失时是推导、报错还是跳过；不允许静默返回“完成、零结果” | 每种缺失一个测试，断言按所写行为处理；设计和计划里的示例配置都作为夹具在引擎里跑一遍，断言产出非空 |
| 失败时回滚（“先回滚再写失败状态”） | 哪些写入要在失败后保留（续跑要复用的中间结果、缓存）、哪些随回滚撤销；需要保留的用独立提交的连接或逐条提交 | 在执行中途注入崩溃，断言已完成的中间结果仍在库中，续跑时不重算、不重复调用外部服务 |
| 测试使用真实数据库连接 | 连接由一个共享夹具创建，并在用例结束时统一关闭；不在各测试文件里各写一份 | 故意让一条断言失败，确认整个测试会话不会挂起；执行者报告“挂起”时，先查数据库里停在事务中的连接 |
| 设计中写明“锁定、随代码发布”的内容（免责声明文本、敏感词表、编码表） | 每一项都有负责的任务卡，并给出确切内容或来源；不能留给读取它的那条线临时写死 | 内容文件存在且非空；读取方在内容缺失时按 fail-closed 处理 |
| 按字段修改结构化内容的接口（编辑文档块、修改配置项） | 每种对象类型允许改哪些字段、值的形状（例如表格行的列数），其余字段、其余类型和空请求一律拒绝；只写“段落改 text、表格改 rows”不够，还要写不匹配时怎么办 | 每种不匹配各一个测试，断言被拒绝且没有写审计或修改记录；每种允许的修改各一个测试，断言修改真正到达最终输出（渲染、导出），而不只是存进了数据库 |
| 除主入口外，还有别的入口也“建记录再入队”（试跑、基线、重跑、补发） | 主入口定下的入队规则（同一事务里建记录、入队、提交，入队失败就回滚并返回可重试错误）逐个套用到这些入口；去重查询不得返回一条永远不会推进的记录 | 每个入口一个“入队失败后不留记录，恢复后能正常创建”的测试 |
| 计划写了“去重”“防连点” | 当作先查后写的竞争处理：去重查询前加锁（例如按去重键的 advisory lock）；顺序点两次的测试证明不了任何并发问题 | 两条连接、线程屏障同时发起，断言只建一条记录、两次返回同一个 id |
| 两条线通过存储交接数据（一方写文件，另一方读） | 写入方的 bucket 和 key 格式、读取方从哪个 bucket 按哪个字段读，写进跨线约定；两边不一致时谁负责转换 | 用写入方的真实接口写入，再走读取方的真实流程读出，断言字节一致 |
| 记录按外部身份归组或计数（客户、会话、限额、套餐都挂在某个外部用户标识下） | 外部标识为空或缺失时的行为：拒绝并零副作用，不得用空字符串建一条记录；否则所有缺标识的请求会合并成同一个“人”，共用额度和权益 | 标识为空、缺字段各一个测试，断言没有建任何记录、没有入队、没有调用外部服务 |
| 插件声明的标识符受宿主命名规则约束（队列名、定时任务类型、存储 bucket、权限 id 的前缀或字符集） | 逐个查宿主源码里**运行时**才检查的规则（例如 worker 启动时校验队列前缀），写进契约并给出常量；宿主的校验工具和组合工具通过，不代表运行时会接受 | 契约波一个守卫测试：从清单和代码里收集全部此类标识符，断言符合宿主规则；代码中不得出现旧名字面量 |
| 计划逐字给定的面向用户文字（发现项标题、文案常量、菜单名） | 点名测试把这些文字写成字面值断言；执行者认为应改时按偏差报告，不得直接改写 | 每项一个“与计划原文相等”的参数化测试；只测公式和数值时，执行者会顺手“改进”标题，测试全绿、偏差也不报告 |
| 逐字文案由内层函数返回，外层入口还会再加工（加记录标签前缀、包装成模板、截断、拼接追问） | 期望值按用户最终收到的那一层写：写卡前沿调用链从内层函数一直查到对外出口，列出每一层对文本做的改动；前缀或包装依赖数据（标签取自房号、描述、位置）时，写出测试数据下的完整字面值，并核对拼出来的结果是否通顺（两个来源取自同一句原话时会重复） | 经对外入口调用，断言完整字面值（含前缀），期望值写字面量，不调用生成前缀的函数来拼；现有测试只在标签恰好为空时断言无前缀文案，照抄它们的写法会在有数据的场景里变红 |
| 计划给定菜单、按钮或列表的选项文字（序号、项目符号、快捷键提示） | 分清哪些属于选项数据（label）、哪些由宿主渲染时添加：写卡前查宿主的渲染代码，计划里给出的是 label 本身，并注明宿主会加什么；只给“看起来的样子”（`1. 确认`）时，执行者会把序号写进 label，用户看到“1. 1. 确认” | 断言 label 列表等于给定值，且没有一项以数字或项目符号开头；可能的话，再把宿主渲染函数作用在 label 上，断言渲染结果 |
| 内容引用有生效期的参考数据（法规、费率、编码版本） | 计划里的引用表按每个适用年份核对生效期，不只核对 ID 存在 | 测试按每个适用年份断言引用有效；计划作者写表时用同一检查跑一遍 |
| 主事务提交之后才发生的副作用（发送文件、调用外部服务、发通知） | 它的失败出口：提交后抛出的异常不会经过前面任何一处失败处理，必须单独写“失败时转人工或记录状态”，不能只覆盖外部接口本身抛异常这一种 | 让副作用之前的每一步（读文件、取标识、外部调用）各失败一次，断言状态不会停在“进行中”、不向外抛异常 |
| 失败时写一条记录留痕（拒绝记录、错误日志行） | 这条记录本身也要满足表约束：外键指向的父记录可能不存在，唯一键不能用固定占位值 | 同一种失败连续触发两次、以及父记录不存在时各一个测试，断言不抛异常 |
| 要求“在某函数之后调用”，而调用点在另一个文件（路由、任务处理函数） | 把调用点所在的文件列进本线范围，或另派任务；只写函数名时，执行者只能在测试里手动串联两个函数 | 经调用点（HTTP 路由、任务入口）触发的测试，不得手动串联 |
| 任务卡读取已有代码写入的字段（时间、责任人、版本、外键、source） | 查首写及后续领取、重试、改派等改写位置；区分当前值与历史快照、同名字段的命名空间及关联规则；只读参照已有写入方，确需修改才纳入范围或另派任务 | 从实际 producer 取得非空样例，走完可能改写字段的路径再断言；只调用真实 insert API 但自行编造来源值仍不算生产语义验证 |
| 一条线新增一种数据形态（没有金额的发现项、新的严重程度、空列表），另一条线的转换或渲染会处理它（金额护栏、表格转换、排序） | 列一张交叉表：每种新形态 × 每个级别的每个转换和渲染，写明预期输出；两条线并行时，指定合并后由谁跑这张表 | 合并后用真实全链路每个级别跑一次，断言运行成功且该形态的输出符合交叉表；单线测试里构造不出另一条线的数据形态 |
| 按位置定位内容（某编号之后、下一编号之前的表格；某标题下的段落） | 定位锚点必须只属于被定位的对象：不能用在合法范围内也会出现的通用词（例如红框里也有的“YYYY年”）；写明锚点取法，并在源文档上核对一次 | 同页相邻的两个对象，后一个的内容不得归到前一个（最难的布局）；只把内容放到另一页的测试会被按页筛选碰巧通过 |
| 后续阶段的任务会扩充已有清单（技能、方案、目录、计划节点） | 已有测试中对这些清单的相等断言（`==`、固定计数），由契约波改为“已有项都在、新增项在计划表内”，并点名最后一波的任务改回完全相等；不留给扩充清单的各线自己改 | 契约波里注入一个计划外的条目，断言测试报出它的名字；最后一波恢复相等断言 |
| 单线任务往注册表、枚举或清单里加一项（消息类型、权限项、状态值、技能） | 写卡前在测试目录里检索这份清单的相等断言和固定计数；命中的测试文件列进本任务的文件范围，并给出加项后的完整期望值（新项追加的位置、整列表仍用相等断言）；只写“追加一条断言”时，执行者会撞上旧测试，只能停下报告 | 被锁的测试按新期望值通过；把期望值改成 `in` 或子集判断不算完成，验收时注入一个计划外的条目，确认测试会报错 |
| 任务卡断言状态转换带来的字段变化（计数加一、字段清空、版本号、轮次） | 点名写这个字段的 SQL 或函数及行号；分开写“转换本身写了什么”和“后续步骤（派单、重开、补偿扫描）又写了什么”；结果随配置模式（指派/抢单、开/关）不同时，前置状态里固定模式，每种模式各写一组预期；后续步骤还会再改的字段只断言转换保证的关系（例如“大于”），不断言精确值 | 每种模式一条测试，预期值与代码里写入该字段的那一行对得上；凭印象写的“退回后轮次加一”在只清空责任人、不动轮次的实现上必然失败，执行者只能停下报告 |
| 按候选数量走不同分支（一个直接用、多个出菜单、按名字唯一匹配） | 0、1、多三档都写明行为；0 个候选时不得出一个没有选项的菜单或空列表让用户选，要写明是跳过这一步、退回追问还是报错；候选来自镜像或上游数据时，写明字段为空的那部分数据会落到哪一档 | 三档各一条测试；0 档用会让候选为空的真实数据构造（例如上游字段为空），断言没有空选项的菜单，并断言用户下一步有路可走 |
| 用户给出限定词（楼栋、型号、日期、账户），同时有按其它条件匹配的兜底（唯一匹配就直接用） | 限定词能识别、但与匹配结果冲突时的行为：报冲突、追问，还是改用匹配结果；默认不得静默改用另一个对象。分别写“没给限定词”“限定词认不出”“限定词与结果冲突”三种情况 | 冲突情况一条测试：断言回复点名冲突（说出限定词和对象），零写入；另两种情况各一条，行为与无限定词时一致 |
| 新增只给部分身份使用的能力（员工专用技能、开通后才有的功能），宿主用模型或规则把请求分派到能力上 | 宿主的候选集合是否按身份过滤（查宿主源码，不按权限等级字段推断）；“调用时拦截”不等于“路由隔离”——请求被分派到无权能力时，用户只拿到一句拒绝，而不是本该得到的答案。写明用宿主的哪种可见性机制让其它身份根本看不到它（例如“授权后才可路由”），以及其它身份说出相近的话时应去哪里 | 每种身份的授权集合下各断言一次候选集合（无权身份不含、授权身份含）；再按身份跑真实模型对照：目标身份的正例、其它身份的相近说法、目标身份的日常反例 |
| 修改路由描述、关键词或意图示例（新增技能、补一类说法） | 安排真实模型的对照实验并写明做法：现网原文从基线提交导出、不读正在修改的工作区；断言最终分派结果（含宿主后处理），不只看模型输出；每种身份按线上授权口径各跑一遍；回归既有题库；每句至少两遍，并区分现网版本自身的抖动。补进描述或关键词的词要检查会不会把相邻意图的提问拉进来（为“公区有异味”加的“有异味”会吸走“房子有异味吗”这类咨询） | 对照报告：正例命中率、反例被抢数、题库里两遍都变化的条目逐条说明；现网自身两遍就不一致的条目单列，不算本次引入 |
| 声明端到端时间预算或容量限制 | 哪些真实阶段和循环消费同一预算；容量检查覆盖哪些实际输出；错误由谁转成稳定结果 | 让真实读取／统计／渲染中途耗尽预算、让每种输出超限，断言结构化失败和零部分发送；mock 掉该阶段只证明调用方，不能作为阶段保护证据 |

场景：计划的 Review Focus 写了“审批冲突”，只举了“先批 A 再批 B”的顺序例子。执行者据此写了过期版本检查和顺序测试，全部通过；两位审批人同时批准基于同一版本的两份草稿时，两份都进入已发布状态，先批的内容被静默覆盖。若计划把这条“先检查后写入”的规则写成竞争条件，并指定双连接加屏障的测试，执行者就会写出 CAS 条件和 rowcount 检查。

场景：一个“已编辑后，上游升级应生成待合并草稿”的测试，用一条 `update` 直接把记录标成“已编辑”。真实编辑流程不会写比较基准所用的字段，测试却一直是绿的。计划写明“先经编辑并发布的生产流程构造前置状态”，这个缺陷在第一次运行时就会暴露。

场景：计算组件把单元格里的 None（原文为“-”，表示未知）当成 0。申报数未知时，差异等于账面数，下游据此算出了虚构的应缴金额和罚款。计划的 Review Focus 写了“缺失不是 0”，但只把测试指派给了解析器等生产方；如果每个计算任务卡都有空值规则表，这条路径在编码前就会被定义。

场景：计划只写“正文里的文号必须在法规库中”，没有列出输入形态。执行者只处理了最规整的写法，方括号或全角括号的变体、数字前后带空格的写法，以及发文机关写错但年份和序号正确的文号，都通过了校验。同一份计划为模型输出的数字溯源列了变体，却没有为同类的过滤和校验规则列出。反过来，数字溯源自己的变体也要列全：负号或“下降”这类方向词、中文数字、结构化输出中的数值字段，以及“年份豁免”被“2000元”这种写法利用。

场景：计划写了“中间层读取过滤后的视图”，测试也只断言了这个视图。最终返回值里仍带着敏感项，内部专用的键也泄漏了出去；执行报告点名的规则测试都存在且通过，但没有一个断言到出口。

场景：计划让后台接口的测试“用假的认证依赖返回当前用户”。执行者的假依赖不需要任何参数，于是实现里不带参数直接调用它；宿主真实的认证依赖需要凭据，调用失败后异常被吞掉，代码退回到“默认租户的管理员”。全部测试通过，生产环境中却不登录也能以管理员身份调用所有接口。计划若写明替身必须要求凭据，并点名“未认证返回 401”的测试，这个缺陷在第一次运行时就会暴露。

场景：同一轮里，“显示真实名称”开关的测试数据里根本没有代号，空实现原样返回也能通过；文档解析警告存进 JSON 列后读出就是列表，组装阶段又把它当字符串解析，但样本文档恰好没有警告；“已通知”标记被失败通知占用，运行失败、重跑成功后，初稿就绪的通知再也没发出。三个缺陷的共同点是：测试只走了数据为空或流程只走一遍的路径。

场景：一条运行流程线的组合测试全部通过，用的是照抄设计示例写成的最小种子。合入完整种子后的第一次运行就失败了：内置算子靠导入副作用注册，生产代码里只有一个后台接口会先调用加载函数，而内容线的测试都手动调用过它。修好之后又发现，设计示例里的按年规则没有声明年份列表，引擎遇到这种情况静默返回零发现，所以最小种子上的组合测试从来没产出过一条发现。同一轮的返工单要求“失败时先回滚再记状态”，却没写已完成的节点结果要保留，结果崩溃一次，续跑就要把所有模型调用重付一遍。

场景：幂等测试断言两次导入结果相等，但生产种子目录要等后续开发线填充，现在是空的，两次都导入 0 项，天然相等。计划指定夹具并要求“第一次导入数量大于 0”，测试才会真正检查去重。

场景：一份报表计划的点名测试很多，黄金值只给了总体指标。“未知状态也要让受影响分组的完成率待核实”“读取、统计和逐行渲染都检查同一时间预算”“内部枚举显示中文”这几条只写在实现段落里；预算的点名测试只断言“超时后发送 0 次”，在发送前检查一次就能通过。首轮交付中这几条全部未做到，返工一轮后分组未知和阶段内预算仍未做到；分组只有一两个计数，因为没有分组的黄金值可核对。若计划把每条要求挂到一条会让偷懒实现失败的断言上（直接调用真实渲染器并让预算在行循环中耗尽；给每个分组一组字面值），这些缺陷在执行者自己的红绿循环里就会暴露。

## 黄金值与规则测试

计划里的每个黄金值，写计划时都要用脚本从原始资料重算一遍，并在旁边写出公式和输入原值，便于执行者核对。手算或估算的黄金值一旦写错，执行者只能在“改断言”和“停下报告”之间选择。

任务卡的每一条计算规则（分段、跳过条件、名称归一、备注文字等），都要有一个点名的测试。黄金样本测试只覆盖一个样本的正常路径，不能代替规则测试；只给黄金样本时，执行者通常每个组件只写一个样本测试。

黄金值要覆盖每个承诺的输出维度：总体之外，每种分组（按地点、类别、人员等）、每张表、说明页都要有字面期望，至少给出每个分组的指标集合和一组数值。只给总体黄金值时，分组往往只实现一两个计数，验收也没有字面值可核对。某个维度确实不提供黄金值，写明由哪条点名测试用字面值证明。

抽取、解析、导入类任务，每个表格型数据项除了抽样黄金值，还要断言**完整性**：行数或键集合等于原文（例如“36 个月齐全”“13 行”）。抽样值只能证明“取对了”，不能证明“取全了”；一张 36 个月的表只抽 2 个月时，续页丢掉 9 个月也能全绿。

源文档自带的勾稽关系（合计行、小计、“应计 − 已申报 = 差额”这类恒等式、同一个数在两个章节出现的交叉引用），计划要逐条列出，作为对每一行都成立的**全量**断言；它能一次抓住跨页丢行和取错列两类问题。合计值由解析器从原文读取，不在测试里硬编码后再拿来比较，否则就成了自己验证自己。同时把这些勾稽关系写进运行时的数据质量校验（作为 warning），换了新样本也能兜住。

黄金值有异议时，保留原断言并报告偏差。把字面值换成“用同一公式再算一遍再比较”，测试就永远不会失败；验收时检查断言右侧是不是字面值。

## 计划内部一致性自查

交付计划前，逐项核对：

1. **规则 ⊆ 签名。** 任务卡里的每条规则，都能用该任务函数签名给出的参数算出来。例如要求“校验引用的条目都存在”，签名里就必须有可以查询这些条目的参数；否则执行者做不到，只能报告偏差。又如报告组装要按“该章节的数据项由哪个节点产出”显示未完成原因，签名里就要有数据项到产出节点的对应关系；缺了这项输入，执行者只能猜，结果会把别的节点的失败原因安到这一节上。
2. **设计收窄要写明。** 逐条核对任务卡引用的设计章节。计划收窄了设计要求的（例如设计要求所有状态变化都写审计，计划只在批准时写），明确写出收窄内容和理由。渲染类任务尤其容易漏掉页脚生成时间、水印、品牌等设计要求。
3. **按宿主接口的实际参数写契约。** 宿主接口不带的上下文（例如审计接口没有租户参数），计划要写明放进哪个字段（例如 detail）。
4. **提交责任不自相矛盾。** “调用方负责提交”和“按租户缓存、只执行一次”同时出现时，写明标记在谁的提交之后写入。
5. **规则文字与点名测试一致。** “加载 N 个条目”这类数字，与同一张卡里的清单逐项对数；每个点名测试的预期，与卡内的规则、默认值、接口说明相符。例如卡里既写“渲染地址有默认值”，又点名“缺少地址时报错”的测试，两者不可能同时成立。
6. **跨线共用的类型和判定逻辑放进契约波。** 包括协议的返回值类型，以及校验器、规范化函数、格式化函数；或者指定唯一负责线，另一条线只调用。自查时查找两张任务卡里描述相同的规则。见 [parallel-waves.md](parallel-waves.md)。
7. **每个产出都有消费方。** 每个被产出的数据项都至少有一个消费方（下游节点或报告章节）。只有生产、没有消费的，要么补上消费方，要么删掉；例如大模型技能照常运行，却没有任何章节展示它的输出，只是白白消耗调用。
8. **内容卡用到的能力，引擎都已提供。** 内容类任务（规则、模板、提示词）写的每个占位符、函数和字段，在执行它的引擎里都要已经支持。例如规则说明要引用另一个数据项的当年值，而模板渲染只支持年份和数值，执行者只能停下报告。
9. **只写“按设计第 X 节”的规则，要把公式和清单抄进任务卡。** 例如“预计时间按设计 11.1 计算”，卡里要写明“同一方案最近 20 次运行耗时的中位数，没有历史时取 5”；只给章节号时，执行者容易直接写死默认值。字段清单、分组维度的指标集合、枚举显示文字同理。交付前在计划和返工单里检索“按设计”“见设计”“设计 §”这类引用，逐条展开或写明为何只需引用。
10. **黄金值与同卡的阈值互相核对。** 黄金样本的每个命中年份、严重程度，都按卡内阈值用原始数据重算一遍。例如阈值为 10 万，而某年差额 18 万，黄金年份就不能漏掉这一年。
11. **设计示例与引擎约定一致。** 设计和计划里的示例配置（规则、模板、清单）照抄后必须能在引擎里产出结果。示例省略了引擎要求的字段时，要么改示例，要么让引擎能处理这种省略；最小夹具常常照抄示例，示例错了，最小夹具上的组合测试就全是空跑。
12. **依赖后续线产物的测试，写明合入后补跑。** 组合测试要求“使用某条线交付的完整数据”而那条线还没合入时，计划写明先用哪份临时夹具、上游合入后由谁用真实产物补跑，并把补跑列为该线验收的一部分。
13. **返工单本身也过一遍这张表。** 返工单新增的要求（例如“失败时先回滚”）同样要推导它影响的其他规则（续跑、缓存、通知），否则修一个缺陷会引入另一个。
14. **计划同步时新增的每个预期，都先对照真实运行或宿主源码核对一次。** 中途补写的任务卡最容易凭印象写预期：例如“12 个章节都有内容”（实际样本上有一个章节为空）、“模型调用抛异常会让运行失败”（实际只会让节点降级）、“菜单用某个图标”（实际不在宿主白名单内）。这三条都在交给执行者之前被核对出来；不核对，执行者只能停下报告或改断言。
15. **每条要求都落在本线的文件范围内。** 例如“从技能编辑页跳转到试跑页”，编辑页属于另一条线的文件，本线又只允许修改其中两处，执行者就只能跳过并报告。写要求时同时写清它要改哪个文件，并把这个文件列进本线范围。
16. **同一规则的所有入口一起写。** 全称/共享规则在交接前填好 [源码覆盖清单](rework-control.md#全称契约先核实覆盖清单)，核对别名、包装器、定时/重试及直接写入旁路；每项有契约判定、负责子任务和实际出口断言，不将发现工作全部留给执行者。只读分支也算入口：确认、取消校验了草稿归属，而兜底重显分支未校验，会泄露别人的草稿。消费端补齐后的结果不能证明生产端完整写入。
17. **往清单里加项之前先扫一遍已有测试。** 要扩充的每个清单（注册表、枚举、目录、计划节点），查已有测试里有没有用相等或固定计数锁住它。多线的后续阶段在契约波处理；单线任务把那个测试文件列进本任务范围，并写出加项后的完整期望值（见上表）。不扫的话，第一个加条目的任务就会撞上旧测试，只能停下报告或擅自改测试。
18. **并行线的测试资源互相隔离。** 测试夹具会删建固定的 schema、表或目录时，每条线分配独立的数据库（或 schema、目录），验收方另用一份；写进环境表和测试命令。见 [parallel-waves.md](parallel-waves.md#并行线的测试隔离)。
19. **设计里的发布阻断断言逐条抄进任务卡。** 设计列出的护栏或验收断言（例如“L2 所有金额为区间”），任务卡要逐条照抄并各配一个测试；收窄（例如只检查敞口表）必须写明理由。只抄一部分时，执行者只测这一部分，其余出口照样泄漏。
20. **部分结果的断言先断言整体状态。** 测试只断言“某节点完成”“某条记录存在”时，先断言整次运行没有失败或中止；否则最小夹具让运行中途中止时，测试是否通过取决于节点执行顺序，别的线新增节点后就会变红。
21. **全局约束与任务卡示例互相核对。** 例如全局约束写“说明文字不得手写数字”，卡上示例却写“占比超过50%时”；执行者无论照哪一边，另一边都算违反。写完后把每个示例拿全局约束过一遍，约束要写清例外（例如原报告口径里的阈值可以照写）。
22. **验收卡的每个子句写成一条独立断言。** 一格里写了几件事（“第 1 条；另断言渲染输入无金额”“样本覆盖 54 项；L2 文档该章节显示固定句”），执行者往往只实现第一件；数量词（“各有 1 条”）会被写成集合相等，“退回次数”会被写成“比之前多 1”。写卡时把每个子句拆成一行，数量写成按键计数，状态写成绝对值。
23. **关键字段核对到后续消费者使用时，而不止首次写入。** 点名首写和后续改写的 SQL／函数，按实际配置模式走完领取、重试等路径；固定计算起点前确认字段仍代表所需历史事实。同名字段先定义各自来源和关联键，不因名称一样就要求相等。未核实的指导标为假设并安排在依赖任务前验证，不能写成已确认事实。
24. **逐字文案按最外层出口写。** 卡里给定的文案若由内层函数返回，先沿调用链查到对外入口，确认外层有没有加前缀、包装或截断；有就把完整字面值写进卡里，并用会让前缀非空的测试数据核对一遍。只照内层返回值写期望，执行者在真实入口上测必然对不上，只能停下报告。
25. **文件清单里的每个文件，都用符号检索确认要改的逻辑在它里面。** 例如写“通知渲染改用新的位置文本”，要先检索渲染函数实际在哪个文件，不能按文件名猜（通知的渲染可能在投递任务里，而不在 `notifications` 模块）。写错时，执行者要么改错地方，要么改对地方却不报偏差，验收方要回头核对的范围就变大了。
26. **路由变化的实验由谁跑、何时跑、怎么证明合并后等价。** 真实模型的对照实验通常只有验收方能跑（执行者不调用真实模型）。计划写明：执行者只交付能在单测里断言的部分（清单字段、各身份的候选集合）；验收方在合并前对实验副本跑对照，找到问题时把改法写进返工单；合并后用确定性比较（各身份的候选集合逐字相同）证明与已验证的副本等价，只差注释、换行时不必重跑模型。
27. **实现段落里的要求都落到断言上。** 逐条列出“实现”“修复要求”段落里的“必须／不能／不得”，每条对应到某个点名测试的一条断言，并问：最省事的错误实现（只在总体处理、只在调用前检查一次、只映射已知值）会让这条断言失败吗？对应不上的，要么补断言，要么明确降为建议。已观察到的交付中，只在段落里出现的要求最常被漏做，返工后仍会再漏。返工单同样适用。
28. **黄金值覆盖每个输出维度。** 对照输出矩阵逐个维度（总体、各分组、主表、明细、说明）检查是否有字面期望；缺的补上，或写明由哪条点名测试证明。只核总体的黄金值，不能证明分组和字段已交付。

## 探针验收、根因分类与返工单

**探针验收。** 验收方除了重跑执行者的测试，还要按上表逐条规则写真实流程的探针脚本：重复触发、并发、非法引用、回滚、空夹具。探针放在验收方的临时目录，不进仓库。对计算组件，再加一类契约往返探针：把每个组件的输出按共享契约的类型编码再解码，检查是否无损（这正是执行引擎实际做的事）；再依次输入 None、0、表外枚举和空列表，看会不会崩溃或算出虚构值。对上下游分线开发的组件，再把上游的真实输出喂给下游组件，跑一遍黄金链路。执行者的测试全绿、跳过数为 0，不能替代探针。

另外几项固定检查：

- **对照测试清单。** 把任务卡点名的测试逐个对到实际的测试函数名；缺的列进返工单。报告写“无未完成项”不能代替这一步。名字对上之后，还要打开测试看断言是否覆盖卡里写的每一项：卡里要求“开关为 true 和 false 各一次、并检查渲染输入”，测试只断言了数据库里的开关字段，名字对、内容只有一半。
- **对照实现段落与断言。** 把计划和返工单“实现”“修复要求”里的每个“必须／不能”对到实际断言；对应不上的列为未验子句，用探针补验，不因测试全绿而视为已交付。
- **核对被验逻辑和完成主张。** 用 [delivery-evidence.md](delivery-evidence.md) 的子句证据表核对真实输入、保留逻辑、替换边界及最终断言；纯计算黄金值不能代替文件出口。红灯区分导入失败与业务断言失败，测试分项／总数以该 SHA 的实际结果为准。
- **首轮覆盖关键生产模式，返工逐项闭合。** 优先验证会改写时间、来源或责任人的真实路径；独立复核候选的实际路径与作者覆盖清单，检查共享 helper 的旁路和消费方，再按子句核对出口断言。未实现项继续列出，不用公开样例全绿或同名新测试代替关闭证据；先前偶发失败也不能只凭连续绿归为环境问题。
- **查找空转断言。** 搜索包在 `if`、`for` 里的断言：条件不成立或循环为空时，断言根本不执行。可选内容要先断言它存在，再断言它的内容。
- **用真实签名替换替身。** 对认证、存储这类宿主接口，按宿主源码中的真实签名重写一个替身，把执行者的测试或探针再跑一遍。
- **跑最严格的宿主检查。** 有构建或类型检查命令时一定跑，不只跑结构校验；结构校验通过、构建失败的情况真实出现过。
- **上游合入后用真实产物重跑。** 下游线用临时夹具开发的，上游合入后先把主干合进下游分支，再用真实产物跑一遍下游的组合测试和一次完整流程。
- **测试挂起先查数据库。** 执行者报告“挂起”或“疑似连接耗尽”时，在挂起期间查数据库的活动连接：停在事务中的连接通常就是没关闭的测试连接。修好清理之后，被挂起掩盖的真实失败才会出现。
- **先核对交付状态。** 收到交付报告后，先看工作区 `git status --short` 为空、HEAD 等于报告里的提交；有未提交的修改就不验收，请执行者提交后再报。
- **检查断言能不能失败。** 断言命中的内容若来自模板固定文字（章节标题、表头），功能删掉也照样通过；同一函数里先检查、后又被另一段代码覆盖结果的，校验等于没写。对返工中新增的每个校验，用探针构造一个应被拒绝的输入确认它真的拒绝。
- **每次合并后跑全链路样本。** 每合入一条线，就在合并结果上用真实样本把每个级别各跑一次并检查输出，不只跑测试；跨线数据形态的缺陷只在这一步出现。
- **合并冲突解决后跑真实构建。** 两条线都在同一文件末尾追加时，冲突块外共享的结尾行（例如右花括号）会被挤到错误位置；结构校验发现不了，只有真实构建或类型检查能发现。
- **验收运行被中断先查环境。** 全量运行出现成批的连接失败、或进程没有输出汇总就退出时，先查共用容器的启动时间、数据库日志和进程列表，确认是不是别的线重启了容器或结束了进程；是的话先停下通知各线，不要反复重跑。
- **清理以“目录不存在”为准。** 在只读仓库里留下的构建目录（例如组合输出、发布暂存目录）若被忽略规则排除，`git status --porcelain` 为空时它也可能还在。执行者报告“路径太长删不掉”时，Windows 上用 `Remove-Item -LiteralPath '\\?\<绝对路径>' -Recurse -Force` 删除，并以 `Test-Path` 为 False 作为证据；交接文档直接写这条命令。
- **外部资料核对只认原文。** 用网页抓取或摘要工具核对参考数据时，要求逐字摘录原文；摘要工具可能编造字段值，只给结论不给原文的不算证据。

**根因分类。** 每个缺陷先归类，再决定改哪里：

| 类别 | 判断 | 去向 |
| --- | --- | --- |
| 计划事实错误／语义缺口 | 写错生产事实、遗漏后续改写、同名字段含义不清，或要求相互矛盾／不可实现 | 作者先修正指导、证据及受影响任务；再安排回归 |
| 执行遗漏／偏差 | 已明确且正确的要求未做到；夹具或替身绕开被验行为 | 修复实现和业务回归，逐子句复验 |
| 修复回归 | 为修一个反例改变共享逻辑，破坏原本合法路径 | 补原反例与应保留对照，检查所有受影响消费方 |
| 验收遗漏／探针过度约束 | 关键旧路径此前未验，或探针对未冻结的内部等价表示作了额外限制 | 记录覆盖缺口；按原业务契约补验或修正探针，不追加隐含需求 |
| 新增需求 | 原批准契约没有要求该行为 | 单独提出范围及决策，不伪装成原交付缺陷 |

按“原规则 → 计划指导 → 生产事实 → 实际断言”归因；一项缺陷可以同时有作者指导错误和执行验证不足。既不把作者事实错误统称编码质量差，也不因执行者守边界就推定全是计划缺口。

**返工单格式。** 返工单也是交给执行者的计划，按下列格式写：

```text
执行条件：前置状态经真实流程构造；提交粒度沿用批准计划／仓库约束；逐项给业务红绿证据，不伪造旧测试历史。

X-R1 问题：复现步骤与实际结果（来自探针）
     依据与归因：原规则、计划指导和生产事实；作者／执行／回归／验收责任可并存
     修改要求：精确到函数和 SQL 条件（例如 where 子句、唯一约束、CAS 条件）
     测试：原反例、相邻模式及应保留对照；实际入口、不能 mock 的逻辑、最终断言；并发类写明屏障
     闭环：该子句的修复提交、实测结果和出口证据；未覆盖子句与负责人继续保留
X-R2 ……
```
