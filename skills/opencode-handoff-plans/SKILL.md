# 编码代理交接计划

目标是让执行者在编码前知道“做什么、依赖什么、怎样证明完成”，让评审者按相同标准验收。根据任务风险决定细节，不以篇幅、任务数或测试总数衡量质量。

本技能只指导计划及评审材料；不自动授权实现、部署、真实发送、数据库变更或代理并行。遵守用户指定的执行分工与仓库工作流。

## 优先让交接可关闭

跨模块或已经返工的任务，先读 [references/rework-control.md](references/rework-control.md)。先形成短的验收子句清单，再按风险选本技能后续参考，不把所有检查项复制进每张任务卡。

- 任务按可独立验收的结果拆分，不用“完成Hub层/管理层”包住多个独立失败条件。总测试数、测试函数名和模块提交不是子句闭合凭据。
- 已知缺陷交付可运行的公开最小回归，先由作者核实输入、替身和允许结果；独立验收另留变体。不能用“保留对抗探针”为由不交接已知失败的复现。
- 对共享逻辑，选出受影响入口、阶段和最终出口，验证修复覆盖的是不变量；既有可接受降级、内部等价表示和作者负责的环境关口在开工前说清楚。
- 批量迁移先安排一条非默认输入经过真实入口、投影和消费者的贯穿样例；新增可选参数的默认值可能掩盖漏传，显示文字也可能是下一步用户输入协议。将调用传播、缓存刷新和回执重建纳入同一关闭凭据，见 rework-control.md 的“先贯穿再批量”。
- 在会影响下游的契约/状态/持久化结果处设小范围阶段复核；同类问题再次漏修，先纠正任务、夹具或语义模型，再扩展返工单。已闭合且未受影响的部分继续保留关闭。

把关键门槛填进任务卡的关闭凭据：实现与验证分别记状态；同一边界样例贯穿重复表达该规则的层；高风险判据先由指定检查者核实，再放行依赖它的任务。具体字段见 [任务卡](references/task-template.md)，跨层与生命周期反例见 [交付证据](references/delivery-evidence.md)。

## 选择交接精度

先确定交付模式：**契约式计划**固定行为、接口与验收，保留实现选择；**精确执行计划**用于设计已定、需要按参考实现逐步复现的任务，提供新文件全文、已有文件的唯一匹配「查找 → 替换」及逐步验证。用户要求逐字执行时采用后者；参考实现未演练时如实标注，不能声称已验证可直接应用。

输出密集时，可附作者编写的冻结端到端字面样例；已有缺陷则另交付可运行的公开回归，两者不互相替代。独立验收保留尚未公开的变体，不扣住已经发现的业务反例。冻结前提见 [references/delivery-evidence.md](references/delivery-evidence.md#冻结验收测试与事实层检查点)，重复返工的处理见 rework-control.md。

编写精确执行计划、独立工作树交接、环境表、红线或偏差处理规则时，读取 [references/exact-handoff.md](references/exact-handoff.md)。先消除重复锚点等可发现的缺口，再交给执行者；不要把选择目标位置的责任留给逐字执行者。

设计负责决策及理由，计划负责操作及验证，交接说明负责开场提示词、阅读顺序、红线、偏差处理和回报。按规模合并文档也可以，但各项只有一个权威来源。引用旧交接时指明适用章节；历史分支、工作目录和发布权限不随引用继承。

## 先确定交付依据

读取当前 spec、相关生产入口、现有适配器/测试夹具、仓库约束及执行基线。记录已核实、待核实、已授权降级三类事实。无法获取外部证据时明确影响的交付范围，不把未知条件写成已满足。

环境表在交接前逐项实测（服务是否在运行、端口归谁、凭据能否登录、库是否已初始化），不沿用旧计划或笔记；红线除写明允许使用的目标，还要点名同机相邻、不得连接或重建的危险目标。

多个文档冲突时先列出冲突并按用户已确认决策统一。不要悄悄用实现片段覆盖业务规则，也不要把已有规格中的要求在验收时当成新需求。

为重要行为建立可追溯行：

`规则 ID → spec 决策 → 负责子任务 → 生产入口 → 验收场景 → 测试层级/命令 → 所需证据 → 当前状态`

重点检查每条业务规则是否拥有完整生产路径。一个日期计算函数通过，不足以证明库存入口实际采用该日期规则；返回一个布尔标记，不足以证明宿主会消费并执行对应动作。追溯行里的测试要断言到规则生效的出口：只断言中间视图的测试，不能证明最终返回、持久化或导出满足规则。

把生产事实写成固定实现指导前，核对关键字段的完整写入生命周期、同名字段的语义及一个最小真实流程样例；任务卡记录证据、未验证假设与关闭时点。字段重建、跨来源关联、报表或返工任务，读取 [references/delivery-evidence.md](references/delivery-evidence.md)，将适用的证据槽位填进任务卡，而不是只加测试名。

## 先画生产接线账本

对每个会写库、发消息、变更状态或暴露给用户的规则，在拆任务前填一行账本：

`规则 → 外部触发者 → 已注册入口 → 领域服务 → 事务内记录/outbox → 已注册消费者 → 可观察结果 → 入口级测试 → 外部证据状态`

规则声称覆盖“全部”生产/消费分支，或修改共享逻辑时，交接前填写 [经源码核实的覆盖清单](references/rework-control.md#全称契约先核实覆盖清单)，并带入任务卡；不能只把“检查其他入口”留作执行者待办。

账本中的入口、消费者和注册点必须写出**现有或将新增的具体文件、符号和注册位置**，例如 skill manifest 的 `runtime.handler`、插件 `JobHandler`、路由依赖、宿主回调 queue。函数存在、表存在或单测直接调用函数都不能填作“已接线”。计划作者应在基线中搜索函数名和队列名：若只有测试调用、没有 manifest/router/job 注册，账本状态就是 `未接线`，不能写“待集成后完成”。

对跨宿主、插件、队列和外部平台的行为，逐项核查下列关口；同步或纯查询路径不涉及的持久化、异步消费者填写“不适用”及原因，不为填表引入额外组件：

1. **入口可达：** 客户按钮、Webhook、页面或定时任务实际能到 handler；技能要有 manifest 和 handler，HTTP 要有 router，异步任务要有 producer 与注册的 consumer。
2. **身份和作用域可信：** tenant、actor、会话、版本和附件归属来自宿主可信上下文，不能来自请求 body、模型输出或前端隐藏字段。管理员身份与员工/客户身份须分别说明，不能把 admin basic auth 当成员工身份。
3. **副作用完整：** 领域操作在规定事务内写契约要求的状态、审计和 outbox；涉及轮次或 SLA 时一并写入对应快照；媒体先由受控接口保留再写附件记录；失败时对客文案不能称已保存或已发送。
4. **后续消费者存在：** outbox 要有目标映射、claim/retry/dead 策略和已注册 drain；回执和客户选择要有可信 consumer。只“入队”是本地排队成功，不是已通知、已送达、已验收。

为适用关口分别写一个正向和一个“零副作用”反例。数据库竞争还要增加与生产同类数据库的隔离双连接测试；外部平台证据缺失时只把本地关口标 `pass`，外部关口标 `blocked`。

## 按可证明的结果拆任务

一个任务以一个可独立验收的行为或边界为单位。避免将状态机、持久化、鉴权、技能注册统称为一个“实现并测试”步骤。

串行长计划中，下游计算或渲染依赖读取、重建出的生产事实时，在事实层任务之后设中途检查点：用真实生产流程（含会改写时间、来源、责任人的模式）取得投影样例并核对，再展开下游。环境阻塞使事实层后移时，下游任务用的手写夹具只是作者假设，检查点通过前不能报完成。

并行时写明独占文件、公共契约唯一来源、依赖具体到产物/版本、集成负责人和冲突处理方式。优先把共享契约作为前置小交付；测试替身可支持并行开发，但集成完成必须使用真实模块。不要照搬“必须合入 main”或固定串行提交顺序，按实际工作区安排。

多线分波次交付时，契约波由验收方或指定集成负责人串行完成并打标签，各线工作区从该标签创建；契约波产生的 Ruling 和已知的消费方约束先单独提交回计划、标签随之移动，再分发给并行线。并行线各用独立的测试库（或 schema、目录），不得重启共用服务或结束别人的进程；续作阶段的契约波先放宽已有测试中锁住清单的相等断言。交接文档骨架、开场提示词模板、验收检查清单及守卫测试要求见 [references/parallel-waves.md](references/parallel-waves.md)。

每个任务提供：

1. 输入/输出及语义：单位、空值、默认值、错误结果、作用域；存在多种表示时给转换规则。
2. 文件和已有复用点：指出生产调用位置，不只列新增函数。
3. 最小可运行验收：真实构造输入、调用入口、断言结果及副作用；给出夹具来源、工作目录、命令和预期失败原因。
4. 有助于避免实错的实现提示：生命周期、SQL 条件、序列化或协议片段。没有必要时不要预写全部业务实现。提示里的每个“必须／不能”若是验收要求，就对应到第 3 项某条测试的一条断言，且该断言对最省事的错误实现会失败；对应不上的只算建议。只写在实现段落里的要求，执行者最容易漏掉。
5. 完成条件与依赖缺口：哪些证据允许本任务通过，哪些只能标记部分完成。

若任务包含入口、异步投递、媒体、权限或回访，另加一个“生产接线”小节，按上节账本逐项列出 producer、registration、consumer 和证据。禁止把“调用某 helper”“建一张 outbox 表”或“页面已有按钮”作为完成条件。

模板及场景例子见 [references/task-template.md](references/task-template.md)，编写任务卡或检查高风险边界时读取。

## 把含糊要求变成可验证契约

按当前任务选择下面相关项，不把整份清单强塞给小任务。

- **状态机**：列“当前状态 × 输入事件 → 下一状态、版本变化、持久化、外部调用、用户可见动作”。区分普通咨询、显式继续、显式重开、取消、交接与旧选择。检查终态后用户是否真的还有合法恢复入口。限定允许动作，不只检查版本。
- **交互协议与自由输入**：菜单的 label、token、序号点击、`text_selection` 和“其他”两步填写是不同输入形状。状态表要分别写出它们到达 handler 时的 selection/text，并决定空 value 的语义。至少一个组合测试须从真实 Core 续接准备进入 handler，断言客户自由文本写入目标字段；只用手写 `value="__other__"` 的单测不能证明真实文本路径。
- **配置生命周期**：当启用状态、路由规则或删除操作决定副作用时，不能只测试“当前可选项被过滤”。明确配置后禁用、禁用时已有待处理记录、重新启用和删除的行为；在 producer 与 consumer 两端验证，避免旧规则绕过 UI 过滤继续发送。
- **金额/日期**：区分用户输入非法与上游数据未知；写清整数/小数、精度、单位、闭开区间、自然月及业务时区。输入不支持时拒绝或澄清，不局部截取数字。菜单生成器和解析/筛选器用同一语义，边界金额只能进入所承诺的档位。
- **资源/事务**：进入和退出同一个连接上下文；明确提交/回滚责任。数据库版本与 JSON 状态版本一致，CAS 对比旧版本；更新带完整 scope。序列化后重新加载，再执行下一事件，验证日期、金额和对象恢复。
- **数据投影**：查明 normalizer 默认值是否抹掉未知状态；列出明确允许值、缺失/非法值处理、父子实体归属及允许输出字段。不能靠历史兼容默认值生成新的对客确定承诺。
- **外部能力**：把生产方与消费方串起来。API 理论支持、协议字段存在、宿主接收、外部端投递成功是不同证据层级。话术必须与达到的实际阶段一致。
- **身份入口**：先写 actor 的可信来源、可访问数据和允许动作，再写 UI 或 API。若系统只有 admin principal，则“普通员工接单/报结”尚未具备实现前提，应写为 blocked 或先建宿主身份契约。
- **媒体闭环**：附件白名单到达 event，不等于附件已保存。契约中应包含 event asset scope、受控 retain 调用、插件对象 key、附件记录和失败补偿；转写文本须有来源与状态，不能把语音接收写成已转写。
- **可靠通知**：路由的“责任人 ID”不天然等于可投递目标。明确人员/群 target 的受管映射、生成 event 的事务位置、drain 注册、claim 并发、重试/死信和可报告的投递层级。
- **轮次与 SLA**：包含派单、接单、报结、返工时，写出每次动作对 round、due 时间、事件和版本的具体影响。不能只迁移字段或实现 scan 函数，必须证明派单入口写入它们、扫描器读取当前轮。
- **无副作用分支**：要求“不查询”“不写入”“不发送”时，断言对应函数未调用，而非只检查最终返回文案。失败后继续不等于不依赖外部调用。

遇到一次缺陷，补齐同一语义类别的场景，不仅修复被举出的单句。例如金额解析同时检查上下限、范围、小数、中文数字、歧义与咨询；不要求穷举所有自然语言。

对每条写库、改状态或做计算的规则，从 [references/plan-self-check.md](references/plan-self-check.md) 选择适用场景，写出前置数据、实际调用、错误反例与最终断言。重点检索：竞争与幂等、身份与归属、空值与计算、过滤与输出、状态与续跑、宿主与跨线契约、注册与构建。该参考是按风险选用的场景库，不必把整表复制进每份计划。新增或同步的预期也要先核对生产证据。

## 让测试证明边界

区分单元、真实模块组合、真实数据库/并发、外部沙箱或真机四层证据。根据所作承诺选择所需层级。

单测可替换依赖；集成测试保留本次被验证的链路。例如入口→store→JSON→reload→下一步不能把 store/编解码全部替换成字典。数据库模拟器不能自动“修正”版本不一致，也不能替代实际数据库的锁、唯一约束和事务语义。

涉及数据库竞争承诺时，用获准的隔离环境及独立连接证明。不具备环境就报告该层未验收；不能为通过测试擅自连接生产库、执行迁移或清空共享数据。

对每个重要测试问：若实现犯了预期要防的错误，这条测试真会失败吗？仅模块缺失的 ImportError 能证明尚未实现，不能证明业务反例被覆盖。只比较 SQL 字符串或预设常量也不能单独证明端到端行为。

对声明生产链路完整的任务，把“从真实入口启动”的组合测试设为交付门槛：它必须保留 manifest/router/job 注册、实际领域服务及本任务涉及的存储或投递链路，断言最终记录或受控 sender 调用。测试可以替换外部网络，但不得替换被验证的 producer 或 consumer。对于声明“客户可操作”“员工可报结”“通知会到群”的行为，至少测试到宿主的受控投递/认证边界；外部真机回执另列为更高一层证据。

### 并发、超时与回复所有权

对竞争、超时、延迟回复或“只发送一次”的承诺，计划必须写出一张**时序与所有权表**：每个参与者可做的 CAS/claim、成功/`false`/异常的处理、谁有权作出同步对客回复、何时建立 durable outbox、哪个已注册消费者负责后续投递。`false` 不是可忽略的日志结果：它表示其他参与者已取得所有权；只有计划能指出那条已持久化且可消费的路径时，才可继续对客返回。存储或转交失败时，不得返回“已排队”“稍后答复”这类承诺，除非该承诺所需的记录和消费者已经在同一原子边界内成立。

把同步回复的最终 claim 放在真正交付给客户的最外层边界；内层 handler、轮询或 worker 只能报告结果，不能先占用会使外层超时后失去补送资格的所有权。worker 写技能完成与登记延迟投递结果有原子依赖时，登记失败、未找到所有权或提交失败必须走可恢复失败路径，不能只记录日志后把工作标为完成。

将“预留请求 → 绑定 event/invocation → 入队”视作一条连续的所有权链，而非三个独立 helper。绑定调用的空返回和异常都表示没有结果登记/outbox 的消费者：必须在入队前终止，回滚同一事务内已创建的记录并返回可重试失败。不得吞掉绑定错误后继续入队，或借用旧协议的标记作为 V2 的降级路径。`failed + output + audit` 只证明问题可追查；除非计划另行注册重入队、修复扫描或人工处置消费者，它不是“可恢复失败”，更不能兑现已经发出的 queued 承诺。

已有严格 XFAIL 或受控复现转绿时，**保留其屏障、事件、挂起点和原断言的交错顺序**。不得把“外层先超时、worker 先完成、最后一次空查”等时序测试缩减为一次 helper 调用后的状态断言。除数据库双连接 CAS 测试外，还要有真实入口 → 执行者/worker → outbox → 受控 sender 的组合测试，在屏障控制下证明每条原始时序恰有一个最终投递或一个已返回的同步正文。报告须列出原复现名称、保留的控制点和实际验证的链路；缺一项即只能算局部存储契约通过。

异步投递的 `retryable_error` 必须有明确上限、退避规则、`dead` 终态与人工/扫描处置方式。固定幂等键、租约重领和“Hub 已接受”可以证明不同层次的行为，不能替代重试终止或客户已收到的证据。

## 交付前与复验

计划交付前完成一次静态走查：每项关键规则有负责人和生产入口；账本的每一行都有适用的注册点和消费者或不适用理由；接口信息够用；happy path 与失败/取消/恢复均可达；关键测试不替换被验逻辑；未确定事项有明确的完成边界。检查表、helper、worker、manifest、router 和 SDK 调用的实际引用：任何仅在测试里出现的生产符号，都要回到 `未接线` 或新建一个明确的接线任务。同时核对：每条规则所需的输入都在函数签名中；汇总数字与明细清单一致，点名测试的预期与卡内规则和默认值一致；收窄设计要求的地方写明了理由；黄金值已用脚本从原始资料重算并附公式；每个产出的数据项都有消费方。

执行报告使用：规则 ID、实际提交、命令与工作目录、pass/fail/skip、覆盖链路、模拟范围、未完成依赖。模块通过、集成通过和外部闭环通过分别给结论。数据安全降级可以验收其降级行为，但不能把尚未实现的业务规则改称完成或擅自转给另一执行者。

复验先用 [references/delivery-evidence.md](references/delivery-evidence.md) 的闭环表检查前轮每个子句及相邻行为，再沿账本从入口走到消费者。按生产证据分别识别计划事实错误、执行遗漏、修复回归、验收遗漏及新增需求；内部等价表示不自动算业务缺陷。不要每轮只补一个样例，也不扩大隐含标准。

具体复验按 [references/plan-self-check.md](references/plan-self-check.md) 的探针、构建、真实产物、清理与环境排查条目选用；不要把整份清单复制为每个任务的固定全量流程。返工单本身也做一致性检查，尤其新增修复对回放、状态、缓存和后续消费者的影响；同类重复漏修按rework-control.md先纠正交接方法，再继续执行。
